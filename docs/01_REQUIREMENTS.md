# 01. 要件定義書

- 対象: stack-summary
- 作成日: 2026-10-10
- 改訂: 2026-10-10（仕様レビュー判定の「直す」5点と「決めた一文」を手順にした）
- 関連文書: [02_SPECIFICATION.md](02_SPECIFICATION.md) / [03_STRUCTURE.md](03_STRUCTURE.md)

## 1. 背景（ペイン）

気になった技術・サービスのメモ（Discord への投稿など）が溜まる一方で、整理されていない。プロジェクトの技術構成（stack）を決めるときに、過去に何を調べてどう思ったかを探し出せない。

## 2. 目的（ゴール）

メモから技術を取り出して分類し、自分の stack の全体図にする。好みの stack を選ぶとき、迷ったときに見返して判断できるようにする。

## 3. 対象範囲

### 3.1 対象

- 形式を問わない文章の貼り付けによるメモ取り込み
- Gemini によるメモ分割・技術抽出・分類（全自動）
- メモと技術の 2 層構造
- 大分類・小分類・タグによる分類と、その管理
- 技術ごとの好み（状態と一言理由）
- stack の全体図、技術の詳細、検索
- データの書き出し

### 3.2 初版の対象外

| 項目 | 扱い |
| --- | --- |
| 構成セット（技術の組み合わせに名前を付けて保存） | 使ってみて必要なら追加 |
| Discord への投稿・投稿文の下書き生成 | 対象外 |
| 意味で探す検索（埋め込み・ベクトル検索） | 対象外。キーワード検索のみ |
| リンク先ページの取得・要約 | 対象外。メモ本文だけを使う |
| 判断モデル（Clef 等）による振り分け | 後から差し替えられる形にだけしておく |
| 自分以外の利用 | 対象外 |
| スマホでの追加・編集 | 対象外。スマホは閲覧のみ |
| 原文を消す API | 初版では作らない。原文は常に保存する（FR-02） |
| 技術の親を指す列（`parent_tech_id`） | 置かない。新機能は親の名前で照合する（FR-13） |

## 4. 利用者

篠田 1 人。PC で取り込み・編集・閲覧を行い、スマホでは閲覧だけ行う。

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| メモ | 取り込んだ文章を Gemini が区切った 1 件分の技術メモ。本文は表示用の断片であり、同一性の判定には使わない |
| 技術 | メモに出てくる技術・製品・サービス（例: Hono、Ubicloud） |
| 大分類 | stack の大きな区分。初期値は 9 個。追加できるのは利用者だけ。技術の行には大分類の列を持たない |
| 小分類 | 大分類の中の「比べる枠」。同じ小分類の技術同士は代替関係にある。空なのは未分類だけ |
| タグ | 話題・ベンダー・使っているプロジェクトなどの自由なラベル。表は残す |
| 状態 | 技術への好み。採用中 / 試したい / 様子見 / 見送り / 未評価 |
| 関係 | メモと技術のつながり方。主題 / 比較 / 言及 |
| 出所 | その行を書いた主体。利用者（`user`）かモデル（`model`）か。再処理はモデルの行だけを置き換える |
| 確定 | 出所が利用者である項目。再処理で上書きされない |

## 6. 機能要件

### 6.1 取り込み

| ID | 要件 |
| --- | --- |
| FR-01 | 利用者は形式を問わず文章を貼り付けて取り込める（Discord ログ、メモアプリ、記事の抜粋、URL のみ等） |
| FR-02 | 貼り付けた原文は常に保存する |
| FR-03 | Gemini が原文をメモ単位に区切り、技術メモでないもの（お知らせ・雑談等）は除く |
| FR-04 | 取り込みの重複は、原文を正規化したハッシュで判定する。リンク表記は除かない。一致する原文があれば Gemini を呼ばない。メモの本文は表示用の断片とし、リンクを除いた文字列では同一性を判定しない |
| FR-05 | 本文が違うメモは、URL が同じでも重複にしない。URL が重なるときは「似たメモがある」と示す。URL だけのメモは、URL の集合が同じなら同一とする |
| FR-06 | 取り込みはバックグラウンドで進み、利用者は進み具合と失敗を確認できる。終端まで失敗した取り込みは、必ず失敗として残る |
| FR-07 | 取り込みを再処理できる。再処理は同じ取り込み ID に対する自然キーの upsert とし、出所が利用者の状態・理由・タグ・別名・分類は変えない。出所がモデルの行だけを置き換える |

### 6.2 技術の抽出

| ID | 要件 |
| --- | --- |
| FR-10 | Gemini がメモから技術を抜き出し、関係（主題 / 比較 / 言及）を付ける。モデルが返すのは名前、関係、別名候補までとし、既存技術の ID は返させない |
| FR-11 | 主題と比較の技術だけを技術として登録する。言及はメモ側に記録し、後から技術に格上げできる。格上げは FR-12 と同じ照合を通し、言及行は消す |
| FR-12 | 技術の同一性は、別名キーの正規化規則だけが決める。正式名の一意にも同じ規則を使う。全技術の一覧は抽出のプロンプトに渡さない |
| FR-13 | 製品の新機能（例: Worker Previews）は独立した技術にせず、親の名前（Cloudflare Workers）で照合し、そのメモを親の関連メモにする |
| FR-14 | 会社・プロジェクト群（例: Vercel Labs）は技術にせず、ベンダーのタグにする |
| FR-15 | 利用者は 2 つの技術を統合できる。自分自身への統合はできない。衝突する別名・タグ・メモの役割は残す側を残し、同じメモの役割は 1 つに畳む。残す側の確定した分類を保ったまま統合元を消し、統合元の正式名は必ず別名にする。両方に理由があるときは統合せず、利用者に残す理由を選ばせる |

### 6.3 分類

| ID | 要件 |
| --- | --- |
| FR-20 | 技術はちょうど 1 つの小分類に属する。小分類が空なのは未分類だけであり、分類済みの技術は小分類 ID を必ず持つ。技術に大分類の列は持たない |
| FR-21 | 大分類の初期値は 言語 / フロントエンド / バックエンド / データベース / インフラ / 開発ツール / AI モデル / AI 開発ツール / 外部 API の 9 個 |
| FR-22 | 大分類を追加・改名・並べ替えできるのは利用者だけ。Gemini は大分類を作らない |
| FR-23 | Gemini は技術を既存の小分類に振り分ける。当てはまるものがなければ小分類を新しく作る。分類器の戻りは提案であり、実在しない大分類 ID と「その他」相当の名前は未分類にする。小分類の新設は、大分類と名前の一意制約への upsert に閉じ込める |
| FR-24 | 「その他」の分類は作らない。振り分けを決めきれない技術は「未分類」の受け箱に置く |
| FR-25 | 確認一覧に出るのは、Gemini が作り、まだ確認していない小分類だけである。改名・統合・移動を 1 操作でできる |
| FR-26 | 利用者は技術を別の小分類へ移動でき、移動した分類の出所は利用者になる。再処理で戻らない |
| FR-27 | 1 件しか技術がない小分類があってよい。中身が 1 種類しかない大分類では、画面は小分類名を出さない。小分類の行は残す |
| FR-28 | Gemini と利用者は技術とメモにタグを付けられる。タグには種類（話題 / ベンダー / プロジェクト）と出所がある |
| FR-29 | 分類処理は差し替えられる形にし、後から判断モデル（Clef 等）に替えられる。差し替え口は残す |

### 6.4 好み

| ID | 要件 |
| --- | --- |
| FR-30 | 技術に状態（採用中 / 試したい / 様子見 / 見送り / 未評価）と一言理由を付けられる。状態と理由は出所を持つ |
| FR-31 | 新しく登録した技術の状態は「未評価」とする。出所はモデル |
| FR-32 | 未評価の技術をまとめて表示し、続けて好みを付けられる |
| FR-33 | 技術に「使っているプロジェクト」のタグを付けられる（例: line-send） |

### 6.5 見返し

| ID | 要件 |
| --- | --- |
| FR-40 | 大分類ごとに小分類と技術を並べた全体図を表示する。状態は色で区別する。中身が 1 種類の大分類では小分類名を出さない（FR-27） |
| FR-41 | 全体図を状態・タグ・キーワードで絞り込める |
| FR-42 | 技術の詳細で、状態・理由・別名・タグと、関連メモを新しい順に表示する。最終更新日も出す |
| FR-43 | 小分類の画面で、中の技術を状態・理由・関連メモ数つきで並べて比較できる |
| FR-44 | メモをキーワードで検索できる |
| FR-45 | メモの日付（投稿日など）が分かる場合は保存して表示する |

### 6.6 その他

| ID | 要件 |
| --- | --- |
| FR-50 | 全データを JSON と Markdown で書き出せる |
| FR-51 | 画面はすべて日本語 |

## 7. 非機能要件

| ID | 区分 | 要件 |
| --- | --- | --- |
| NFR-01 | セキュリティ | 利用者本人以外はアクセスできない。`/api` は JWT が無ければ常に 403 とし、固定ユーザーへ読み替えない。固定ユーザーの分岐は本番の Worker に入れない。検証には署名、有効期限、発行者、aud、メールを含める |
| NFR-02 | セキュリティ | 秘密情報（Gemini の API キー、本人のメール等）をリポジトリに含めない。リポジトリは Public。`.gitignore` に `.dev.vars` を入れる |
| NFR-03 | セキュリティ | メモ本文を HTML として描画しない。リンクは http / https のみ有効にする |
| NFR-04 | セキュリティ | Gemini の出力は決めた JSON の形だけを受け付ける |
| NFR-05 | プライバシー | 自分以外の発言を Gemini に送る扱いを、利用枠の規約と合わせて決める（§10） |
| NFR-06 | プライバシー | 取り込んだ実データ（他人の発言を含む）をリポジトリにコミットしない |
| NFR-07 | 信頼性 | 取り込みが途中で失敗しても原文は失われず、再試行・再処理できる。終端の失敗は必ず失敗状態を書く。各ステップは自然キーの upsert とし、同じステップが再実行されても二重に増えない |
| NFR-08 | 保守性 | 分類ごとに使ったモデルと指示文の版を記録する |
| NFR-09 | 品質 | 正解付きサンプルで分類の正答率を測れる。テストカバレッジ 80% 以上 |
| NFR-10 | 操作性 | PC（1280px 以上）を主とし、スマホ幅（375px）で閲覧できる |
| NFR-11 | コスト | Cloudflare の無料枠と Gemini Flash 系の範囲で運用する |
| NFR-12 | 運用 | デプロイは main マージで自動実行する |

## 8. 受け入れ条件

| ID | 条件 | 対応要件 |
| --- | --- | --- |
| AC-01 | Discord ログを貼ると、技術メモだけがメモとして登録され、お知らせや他人の雑談は登録されない | FR-01, FR-03 |
| AC-02 | 同じログをもう一度貼っても、原文のハッシュが一致するので Gemini を呼ばず、メモも技術も増えない | FR-04 |
| AC-03 | 「Workers」と「Cloudflare Workers」を含むメモを取り込むと、別名キーの正規化で同一と判定された技術は 1 件にまとまる | FR-12 |
| AC-04 | Laya のメモ（判断モデルが 7 種言及される）を取り込んでも、技術として登録されるのは主題と比較対象だけ | FR-10, FR-11 |
| AC-05 | Worker Previews のメモは、親の名前で照合され、Cloudflare Workers の関連メモになる | FR-13 |
| AC-06 | 利用者が直した状態・理由・タグ・別名・分類は、再処理しても戻らない。モデルの行だけが置き換わる | FR-07, FR-26 |
| AC-07 | Gemini が大分類を新しく作ることはない。実在しない大分類 ID は未分類になる | FR-22, FR-23 |
| AC-08 | 確認一覧には、モデルが作り未確認の小分類だけが出る。別の小分類へ統合できる | FR-25 |
| AC-09 | 全体図で「採用中」だけに絞ると、大分類ごとに採用中の技術が並ぶ | FR-40, FR-41 |
| AC-10 | JWT が無いリクエストは、独自ドメイン・workers.dev・Preview URL のどれから来ても `/api` が 403 になる。欠落を本人に読み替えない | NFR-01 |
| AC-11 | 取り込み途中で Gemini が失敗しても、原文が残り、状態は失敗になり、再処理で完了できる | NFR-07 |
| AC-12 | 書き出した JSON から、全メモ・技術・分類・好みが読み取れる | FR-50 |
| AC-13 | 技術を自分自身へ統合する操作は拒否される。両方に理由がある統合は、残す理由を選ぶまで拒否される | FR-15 |

## 9. 前提と制約

- Cloudflare Access を使うため、独自ドメインが Cloudflare で管理されている必要がある。
- Gemini の API キーは利用者が Google AI Studio で発行する。
- 技術構成は line-send と揃える（Workers + Hono + React + Mantine + D1 + PWA）。画面・D1・Gemini は段階 1 では作らない（03 §4）。
